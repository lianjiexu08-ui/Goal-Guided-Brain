# 离线备份与恢复

工作台备份是 `backups/*.sqlite` 的一致性数据库快照。加密凭据如有配套备份，文件名必须是 `<完整备份文件名>.vault.json`，例如 `daily.sqlite.vault.json`。凭据口令不包含在备份中，需要单独保管。

## 恢复步骤

1. 停止使用目标数据目录的控制端及其他 SQLite 工具。systemd 部署使用 `sudo systemctl stop dsh-workbench`；本地部署使用 `npm run stop`。
2. 在项目目录执行：

```sh
node scripts/restore.mjs --backup /absolute/path/daily.sqlite --data-dir /absolute/path/workbench-data
```

3. 使用原来的 `WORKBENCH_DATA_DIR` 启动工作台。systemd 部署使用 `sudo systemctl start dsh-workbench`；本地部署使用 `npm start`。
4. 检查助手、历史任务、知识和连接。恢复的旧数据库会在启动时执行版本迁移。含凭据备份时使用备份对应的口令解锁，并按实际情况重新关联连接。

恢复程序取得控制端独占锁，以只读方式检查来源数据库的完整性及已知结构。现有数据库先执行 WAL 检查点并生成 `before-restore` 一致性备份，再替换数据文件。现有凭据库也会保存到该备份的配套文件，文件权限为仅当前用户可读写。

没有 `.vault.json` 配套文件的旧备份会保留目标目录现有的凭据库，并输出提示。数据库中的凭据引用可能与保留下来的凭据不匹配；程序不会猜测或删除这些凭据。凭据配套文件在恢复时校验结构，密文认证在使用正确口令解锁时完成。

## 失败恢复

运行中的控制端、损坏或更高版本的数据库、无效凭据文件都会导致恢复中止。不要删除仍由活动进程持有的 `control.lock`；先停止该进程。已经结束的进程遗留锁由程序识别并清理。

文件替换前写入 `restore.pending.json`，保存备份来源和恢复前备份位置。只在恢复成功或回滚成功后清除标记；之前已有未完成恢复时，失败回滚会保留原标记。控制端发现此标记会拒绝启动，避免使用不匹配的数据库和凭据。

文件替换期间出现可捕获错误时，程序会尝试回滚数据库和凭据文件。数据库与凭据是两个文件，无法通过一次重命名保证突然断电时两者同时完成。断电或进程被强制终止后，保持控制端停止，根据标记检查 `backups/*-before-restore-*.sqlite` 及其凭据配套文件，并明确选定完整备份重新执行恢复命令。恢复工具允许处理此标记，普通启动不会绕过它。如果提示自动回滚未完成，应保留 `.restore-*` 目录，直到恢复和核对完成。

数据库备份不包含项目代码、worktree、插件包和其他工作目录文件；这些目录需要单独备份。凭据解锁口令、节点部署配置和外部账号也不会因数据库恢复自动重新建立。
