# Goal-Guided Brain 产品路线图

> 本文是 GGB 的产品负责人文档。它定义产品应该解决的问题、用户如何使用、当前已经具备的能力、明确的产品断点、交付优先级和验收标准。实现状态以仓库代码和测试结果为准；规划中的能力不能当作已经交付。

## 1. 产品判断

### 1.1 产品定位

Goal-Guided Brain（GGB）是一个面向个人的目标驱动型智能体工作台。用户只需要说明想达成的结果，系统通过项目经理理解目标、组建合适的团队、为每个成员选择模型和能力，并把执行过程、产物和验证证据带回同一个团队空间。

GGB 的核心产品对象是“团队”，模型只是可以替换的执行资源。用户长期积累的是团队职责、项目上下文、个人工作习惯、权限边界和验收方式，而不是某一次模型对话。团队可以有不同的专业方向，例如开发、运维、产品或资料整理；团队之间能够在授权范围内互相委派工作。

### 1.2 目标用户和高频任务

首要用户是一个人维护多个项目、同时承担产品、开发和运维职责的技术型创作者或小团队负责人。他们通常有以下任务：

| 场景 | 用户想要的结果 | GGB 应该承担的工作 |
| --- | --- | --- |
| 新项目或新需求 | 把模糊想法变成可执行计划 | 多轮澄清目标、交付物、约束和验收方式 |
| 软件开发 | 真实代码、测试结果和变更说明 | 组建产品/开发/验证角色，隔离工作目录，运行测试并汇总证据 |
| 线上运维 | 诊断问题、执行变更并保留审计记录 | 组建运维团队，区分只读诊断和高风险写操作，要求人工确认 |
| 长期项目 | 记住背景并持续推进 | 保存团队会话、知识、任务、检查点和下一步 |
| 多项目并行 | 不混淆上下文 | 每个团队拥有独立目标、成员、模型、能力、目录和消息 |

### 1.3 产品承诺

每个重要动作都应该回答四个问题：

1. **目标是什么**：当前团队、任务或协作请求要产生什么结果。
2. **谁在做**：哪个团队、哪个成员、使用哪个模型和哪些已授权能力。
3. **做到什么程度**：交付物、测试、验证和人工确认状态是什么。
4. **出了问题怎么办**：阻塞原因、恢复入口、重试边界和需要用户决定的事项是什么。

### 1.4 暂不承诺的事情

GGB 不承诺模型始终正确，也不把“模型回复完成”当作交付完成。真实模型的质量、费用、限流和供应商可用性必须在用户自己的任务集上验证。发布、部署、删除、外部发送和生产系统修改仍需要明确授权或人工复核。跨平台、云端 HTTPS、真实 Linux/Windows 节点和离线持续运行需要目标环境验收，不能由本机单测替代。

## 2. 用户心智模型和导航

### 2.1 两个入口必须保持清晰

**团队招募**是需求发布入口。用户在这里说“我要完成什么”，和项目经理多轮讨论，直到形成 Team Charter。这里可以存在未确认的招募草稿，但它不属于已创建团队，也不应该出现在“我的团队”的长期列表中。

**我的团队**是已经确认并可以持续工作的团队列表。进入团队后，用户查看团队目标、成员、任务、进展、产物和验收证据；新的需求通过“发布新需求”回到招募流程，不能直接把团队动态页面当成新的招募会话。

这两个入口是产品的基础信息架构。任意页面刷新、切换团队、切换角色或返回页面时，都必须保留当前团队和草稿上下文，不得把招募草稿误显示为已创建团队。

### 2.2 建议的主导航

```text
团队招募（发布新的目标）
我的团队
  ├─ 团队概览（目标、状态、成员、风险、最近交付）
  ├─ 团队对话（用户 ↔ 项目经理）
  ├─ 任务与执行（任务组、子任务、运行状态）
  ├─ 产物与验收（文件、变更、测试和证据）
  └─ 团队设置（名称、职责、模型、能力、协作权限）
工作台
  ├─ 助手与模型
  ├─ 能力中心（Skill / MCP / Plugin）
  ├─ 知识库
  ├─ 后台任务
  ├─ 定时与监控
  └─ 模型与凭据
```

“助手与模型”和“能力中心”是配置面，不应该成为普通用户完成一次需求的必经步骤。招募时项目经理可以提出模型和能力建议，只有用户确认团队方案后，这些建议才转换成实际绑定。

## 3. 核心用户流程

### 3.1 从目标到团队

1. 用户打开“团队招募”，输入目标，可附加图片或文件。
2. 项目经理复述当前理解，并每轮只询问会影响团队设计的关键问题：目标、交付物、时间、质量、工作目录、外部系统和权限边界。
3. 用户补充信息后，项目经理保存同一招募会话；草稿在页面切换和刷新后仍然存在。
4. 信息充分后，项目经理生成版本化 Team Charter：团队名称、目标、成员数量、每个成员的唯一职责、输入、交付物、模型建议、Skill/MCP/Plugin 需求、依赖和待确认问题。
5. 用户查看方案并确认；未确认的方案不能创建成员、不能分派任务，也不能显示“已完成”。
6. 确认后，系统按实际工作内容生成团队名称，创建成员实例配置，把团队加入“我的团队”，并返回团队概览。

**验收标准**

- 只输入“帮我做一个可上线的项目”，系统会继续澄清，不会直接生成虚假的团队成员。
- Team Charter 中存在待确认问题时，确认按钮不可完成创建，且页面明确指出缺少什么。
- 确认前后分别检查 `/api/state`：确认前团队处于招募阶段，确认后才出现成员配置和 `confirmed` 状态。
- 团队名称来自已确认的工作目标；用户可以在团队设置中改名，改名后所有团队消息和任务仍属于同一 `teamId`。

### 3.2 团队执行

1. 用户进入“我的团队”中的某个团队，首先看到目标、成员状态、进行中的任务、阻塞项和最近交付。
2. 用户将新需求发给项目经理。项目经理先判断是继续当前目标、创建任务组，还是需要重新澄清范围。
3. 项目经理通过编排工具读取成员和能力，按独立交付物分派子任务；每个子任务都有验收标准和依赖。
4. 成员在隔离目录中执行，写入检查点、消息、产物、测试和验证证据。
5. 项目经理等待成员结果并复核证据，再向用户说明完成项、未完成项、风险和下一步。
6. 用户可以打开任务详情查看执行目录、差异、验证输出和用量；必要时暂停、重试、恢复或人工确认。

**验收标准**

- 每个用户需求都能追溯到一个任务组；每个子任务都能追溯到来源消息和所属团队。
- `completed` 只代表执行结束；没有验证证据时，界面显示“待验收”，不能显示“已验收”。
- 子任务失败时，项目经理能指出失败原因和恢复入口，不重复执行已产生外部副作用的操作。
- 用户切换团队、角色或页面后，原团队对话、输入框草稿、附件引用和任务列表不串到其他团队。

### 3.3 团队间协作

1. 当前团队的项目经理发现目标超出职责，读取允许协作的团队列表。
2. 用户授权的团队白名单和协作开关决定是否可以委派。
3. 源团队发送带目标、验收标准和幂等键的协作请求；目标团队使用自己的项目经理、模型、能力、预算和工作目录。
4. 目标团队完成、失败或阻塞后，把状态和摘要回传源团队；双方保存关联消息和任务 ID。

**验收标准**

- 未确认的源团队或目标团队不能发起协作。
- 重复提交同一个幂等键只产生一条目标任务。
- 源团队不能因为收到消息而获得目标团队的私有消息或额外工具权限。
- 协作失败时源团队收到可操作的状态和原因，用户能从源消息打开目标任务。

### 3.4 附件和草稿

拖拽、粘贴和文件选择都必须传输文件内容。界面可以显示文件名作为预览，但发送请求必须包含附件 ID，服务端保存二进制内容，并在任务执行目录中提供可读取路径；纯文本粘贴仍然写入输入框。草稿应按“团队 + 角色 + 招募会话”隔离缓存，附件不能因为切换团队而泄露到另一段对话。

**验收标准**

- 粘贴 PNG 后，输入框显示附件卡片而不是把文件名写入正文；服务端读取到正确的 PNG 文件头。
- 只发送附件也能创建任务；模型上下文能看到文件名、类型、大小和当前任务路径。
- 切换团队后原附件不出现在新团队；刷新页面后仍能恢复未发送草稿，发送成功后清空草稿。
- 超过单文件、单次和总存储限制时有明确错误，不能创建只包含文件名的伪附件。

## 4. 当前实现审计

### 4.1 已具备的产品骨架

仓库已经形成一个真实的控制平面，而不是只有聊天页面：

- 招募状态包含 `discovery → proposed → confirmed`，项目经理通过 Skill 生成 Team Charter，确认后才物化成员。
- 团队、任务组、执行实例、消息、检查点、任务板、产物、验证记录和模型用量持久化在 SQLite；控制平面有租约、预算、暂停、恢复和迟到结果保护。
- 供应商支持多种协议和有序路由，任务快照保存实际模型、供应商、候选模型和能力配置；任务详情可以解释候选能力、实际选用项和自动回退事件；TypeSafe 被限制为可选结构化决策后端。
- 团队默认使用隔离执行目录，任务会按“请求覆盖 > 团队默认 > 助手默认”解析目录模式；需要共享目录的团队仍可显式选择 `shared`。
- Skill、MCP 和 Plugin 经过安装、固定、健康检查和角色绑定；运行实例只能看到已绑定能力。
- 团队委派有源/目标记录、目标团队独立权限和幂等键；附件有二进制存储、大小限制和执行目录暂存。
- 网页、CLI、HTTP API 和编排 MCP 共用控制平面数据；CLI 支持 `ggb run`、`ggb chat`、`ggb providers` 和可选的 `ggb decide`。
- 测试覆盖招募、模型切换、路由、团队协作、能力网关、工作区、备份恢复、定时任务、附件和 CLI 等后端行为。

### 4.2 当前产品断点

以下断点是下一阶段的实际工作项，而不是文案问题：

| 断点 | 对用户的影响 | 优先级 |
| --- | --- | --- |
| 团队概览、对话、任务、产物分散在多个页面，缺少一条连续执行时间线 | 用户需要在多个入口拼接“发生了什么”和“下一步是什么” | P0 |
| 招募草稿、方案版本、确认和新需求之间的状态提示仍容易混淆 | 用户可能把草稿当成团队，或不知道当前应该确认还是继续澄清 | P0 |
| 任务结果与验收证据的关系不够突出，风险、阻塞和待用户决定事项没有统一入口 | 用户难以判断“模型说完成”是否真的可交付 | P0 |
| 实际模型的费用、延迟、质量和失败率还没有形成长期统计；当前任务级路由候选、选择原因和自动回退事件已经可读 | 用户可以解释单次为什么使用某个模型，但还无法比较模型是否适合该职责 | P1 |
| 跨团队协作已存在后端能力，但用户侧缺少清晰的授权、委派进度和回传入口 | 多团队工作容易变成黑盒委派 | P1 |
| Skill/MCP/Plugin 的兼容性和可信代码边界需要在绑定前更直观展示 | 用户可能把“已安装”误认为“完全兼容且安全可用” | P1 |
| 草稿缓存主要依赖浏览器本地状态，跨设备、跨浏览器和服务端恢复能力不足 | 换设备或清理浏览器后会丢失长期招募草稿 | P1 |
| Linux、Windows/WSL2、云端 HTTPS、节点离线续跑尚未完成真实环境验收 | 无法把本地通过等同于跨平台生产可用 | P1 |
| 已建立招募、Team Charter 确认、重命名、两个团队切换、刷新恢复、草稿、模型切换、失败恢复和二进制附件的桌面/移动浏览器基线 | 后端测试通过仍可能出现未覆盖流程和布局回归 | P0 |
| 能力、模型、团队和任务的删除/归档/恢复策略还需要统一的数据生命周期设计 | 长期使用后会出现历史噪声、孤儿附件和难以解释的配置 | P2 |

### 4.3 当前验证边界

确定性测试可以证明控制平面的状态机、权限和数据一致性，但不能证明真实模型的规划质量，也不能替代真实浏览器、真实文件拖拽、真实供应商限流和真实跨平台节点。所有发布记录都必须把以下三类证据分开：

1. **自动化证据**：单元、集成、HTTP、MCP、类型检查、Lint 和构建。
2. **浏览器证据**：桌面/移动尺寸下的招募、切换团队、草稿恢复、附件粘贴、确认创建、模型切换、任务详情和失败恢复。
3. **环境证据**：macOS、Linux、Windows/WSL2、HTTPS、节点掉线恢复和真实供应商的最小请求。

### 4.4 本次 M0.1 里程碑

本次交付先把最容易造成数据误解和上下文串线的边界收紧：

- 旧版本已有团队会自动归入“我的团队”；新需求会创建独立的招募草稿，不复用已确认团队的消息、成员或会话。
- 未确认的招募空间不会出现在协作列表，不能作为跨团队协作的源或目标，也不会被团队编排 MCP 发现。
- 团队成员会话按“团队 + 角色”隔离，切换团队后会话、任务、草稿和附件引用保持在各自空间。
- 任务详情把执行状态、交付判断和证据列表分开显示；完成任务默认仍是“待验收”，验证命令、代码提交和其他产物会保留在同一交付中心。
- 凭据库主密码不再写入 `.vault_pass` 明文文件；受控自动启动只接受 `WORKBENCH_VAULT_PASSWORD`，管理页解锁仍然是默认路径。
- 新增附件重试、独立招募、协作边界、团队会话作用域、团队附件边界和失败执行恢复回归，当前 `npm test` 为 135/135；`typecheck`、Lint、生产构建和本机双服务冒烟请求均已通过。
- 团队默认执行目录已收紧为隔离模式，并在团队创建表单和任务列表中显示；任务详情新增模型路由证据区，展示实际供应商、模型、候选能力以及自动回退或无可用回退事件。
- 团队动态任务摘要现在包含产物数量和验收状态；团队页的“团队设置”会编辑当前 teamId 的配置，不再误打开新建团队；新增两个团队连续 20 次交替消息的归属压力测试。

已建立 12 个桌面/移动 Playwright 核心流程运行：团队招募导航、草稿跨页面恢复、另起需求隔离、真实二进制附件落盘、Team Charter 确认、团队重命名、两个已创建团队的动态/草稿隔离切换（含刷新恢复）、跨团队模型切换和失败任务详情恢复；另有本地 API fixture 连续 20 次交替切换压力测试，覆盖任务、消息、团队和实际路由归属。浏览器连续 20 次切换、多轮模型招募质量、真实供应商回退以及 Linux/Windows/WSL2 环境验收仍是后续门槛。

## 5. 分阶段路线图

优先级含义：P0 是不完成就不能把 GGB 当作稳定个人工作台的基础能力；P1 是让团队可以长期承担真实开发和运维工作的能力；P2 是规模化、自驱动和生态能力。

### P0：稳定的单人团队工作台

目标：用户可以从一句需求走到一个明确的团队、一个可追踪任务和一份可验收结果，过程中不丢上下文。

1. **重做主流程信息架构**
   - 招募页只负责发布需求、澄清和确认；我的团队只展示已确认团队。
   - 团队概览固定显示目标、当前阶段、进行中任务、阻塞、待确认事项和最近证据。
   - 每条消息、任务、产物和验证记录可以从时间线互相跳转。
2. **统一生命周期和状态文案**
   - 明确招募 `discovery / proposed / confirmed`、团队 `active / archived`、任务 `queued / running / waiting / completed / failed / cancelled / state_unknown`、验收 `pending / passed / failed` 的含义。
   - 所有不可执行原因都给出下一步按钮，例如“回答问题”“确认方案”“配置模型”“重试当前轮”。
3. **把验收证据放到交付中心**
   - 任务完成后自动列出代码差异、测试命令、退出码、输出、产物和模型用量。
   - “执行完成”和“验收通过”分开显示；没有证据时显示待验收。
4. **完成浏览器回归基线**
   - 使用固定测试数据覆盖招募、确认、团队切换、重命名、草稿恢复、附件粘贴/拖拽、发布新需求、任务详情和错误恢复。
   - 桌面宽度至少覆盖 1440px 和 1024px，移动宽度覆盖 390px；刷新和服务端轮询不能重置当前上下文。
5. **完善失败恢复**
   - blocked、模型不可用、能力未绑定、任务租约失效和附件上传失败都显示可操作原因。
   - 重试必须保留原需求、附件、模型候选和幂等关系，并显式创建新的执行尝试。

**P0 发布门槛**

- 新用户从空数据目录开始，10 分钟内能够完成“招募 → 确认 → 创建第一项任务 → 查看验证证据”。
- 连续切换两个已创建团队 20 次，团队消息、草稿、附件、模型和任务列表零串线。
- 浏览器回归用例在 CI 连续通过 3 次；后端全套测试、Lint、TypeScript 和生产构建通过。
- 失败任务都能从 UI 找到原因和恢复动作；不得出现只能刷新页面或手动改数据库的核心路径。

### P1：可承担真实项目的团队操作系统

目标：团队可以稳定运行一周以上的开发或运维工作，用户可以控制权限、模型、预算和协作，并理解每次决策。

1. **任务与交付中心**：按团队/项目/状态查看任务组、依赖、阻塞、产物、验证、成本和负责人；支持筛选、搜索、归档和批量复核。
2. **可解释的模型路由**：展示候选模型、选择原因、工具/视觉要求、失败切换、延迟、Token 和费用；支持团队默认模型、成员覆盖和单次任务覆盖。
3. **协作审批**：跨团队委派前展示目标团队、输入、验收标准、预计预算和权限；回传结果后支持源团队确认、追问和重新委派。
4. **项目上下文和知识**：把团队规则、项目知识、附件、历史决定和检查点分层；支持来源、版本、作用域和过期提醒。
5. **能力治理**：安装前显示来源、版本、兼容性诊断、所需凭据和风险；绑定后显示实际注入的 Skill/MCP/Plugin；支持回退和解绑。
6. **草稿和会话同步**：将长时间招募草稿、未发送附件元数据和会话游标保存到服务端，支持浏览器重启和单用户多设备恢复。
7. **真实环境验收**：完成 Linux worker、Windows/WSL2 worker、HTTPS 登录、节点配对、失联续租和离线恢复的实机测试。

**P1 发布门槛**

- 一个开发团队连续执行至少 20 个任务，任务、子任务、重试、验证和产物都可以追溯，数据无孤儿关联。
- 跨团队委派成功、拒绝、重复提交、目标繁忙和目标掉线各有自动化测试和 UI 恢复路径。
- 同一任务的模型选择、能力快照和费用与实际请求一致；任何回退都有事件记录。
- 至少在 macOS、Linux 和 Windows/WSL2 完成同一组冒烟任务并保存日志。

### P2：个人自治和生态平台

目标：用户可以在预算、时间和权限边界内让多个长期团队持续推进目标，并通过结果证据选择更合适的模型和能力。

1. **目标和计划层**：用户设置长期目标、里程碑、截止时间、预算和风险偏好，项目经理自动维护计划并在关键决策处请求用户。
2. **事件流和主动通知**：任务阻塞、模型失效、预算接近上限、验收等待和定时任务结果进入统一通知中心；重复通知去重。
3. **团队模板和复制**：保存开发团队、运维团队、内容团队等模板，复制时重新确认模型、能力、目录和权限。
4. **模型与能力评测**：基于真实任务集比较完成率、验证通过率、成本、延迟和人工修改量，支持按角色自动推荐路由。
5. **生态兼容层**：在明确兼容性报告的前提下扩展 MCP Resources/Prompts、LSP、平台 Hook、Plugin 命令和第三方助手导入。
6. **远程和离线自治**：云端控制平面在所有者离线时按预算和审批策略运行，恢复连接后提供完整事件和证据回放。

**P2 发布门槛**

- 用户可以暂停、恢复、限额和撤销任何自治计划；高风险动作始终有可见审批记录。
- 过去 30 天的任务可以按团队、模型、能力和结果质量比较，结论来自实际证据而非模型自评。
- 远程节点离线、重复报告、权限撤销和未知外部操作结果都有确定性恢复策略和回放记录。

## 6. 测试和发布纪律

### 6.1 每个功能必须交付的证据

一个功能只有同时具备以下四类内容才算完成：

1. 用户流程说明：明确入口、前置条件、成功结果和失败恢复。
2. 服务端测试：覆盖成功、权限拒绝、重复请求、状态变化和持久化恢复。
3. 浏览器测试：覆盖用户真实点击、输入、刷新、切换和错误提示；涉及文件时必须使用真实 `File`/剪贴板对象。
4. 发布检查：`npm run lint`、`npm run typecheck`、`npm test`、`npm run build` 和 `git diff --check`，并记录未覆盖的真实环境风险。

### 6.2 核心回归场景

| 编号 | 场景 | 必须验证 |
| --- | --- | --- |
| E2E-01 | 新用户从招募到确认团队 | 多轮消息、提案版本、确认门槛、团队命名和成员显示 |
| E2E-02 | 两个团队来回切换 | 消息、草稿、模型、附件、任务和 URL/刷新状态隔离 |
| E2E-03 | 发布新需求 | 新建招募记录，不复用已确认团队的旧消息或成员状态 |
| E2E-04 | 文件粘贴和拖拽 | 真实二进制内容、附件-only 任务、执行路径、大小限制和发送后清理 |
| E2E-05 | 模型切换和回退 | provider/model 精确传递、工具能力约束、失败原因和回退事件 |
| E2E-06 | 任务失败和恢复 | blocked、重试、暂停、恢复、新执行实例和旧结果保护 |
| E2E-07 | 跨团队协作 | 授权、幂等、目标独立权限、状态回传和失败恢复 |
| E2E-08 | 高风险操作 | 预览、明确授权、执行记录、结果确认和未知状态处理 |
| ENV-01 | Linux/Windows/WSL2 节点 | 配对、租约、心跳、工作目录、取消和迟到结果 |

### 6.3 产品指标

指标用于发现产品断点，不用于替代人工判断：

- **首次交付时间**：从第一次需求到看到可验收证据的中位时间。
- **招募有效率**：确认后的 Team Charter 在第一次执行前无需重大返工的比例。
- **上下文保持率**：刷新、切换团队和恢复会话后，草稿、附件和历史消息正确恢复的比例。
- **任务证据完整率**：完成任务中同时有结果、验证记录和产物引用的比例。
- **人工接管率**：模型因权限、工具、质量或阻塞需要用户介入的比例，并按原因分类。
- **路由有效率**：实际选择的模型满足工具/视觉/上下文要求且无需无意义重试的比例。
- **交付质量**：验证通过率、用户退回率、人工修改量和外部操作回滚率。

## 7. 当前执行顺序

作为产品负责人，接下来不按零散界面问题逐个修补，而按以下顺序推进：

1. 先完成 P0 的状态、导航、时间线、验收中心和浏览器回归基线。
2. 再以一个真实开发团队和一个真实运维团队做纵向验收，补齐路由、权限、协作和知识的 P1 缺口。
3. 最后再投入自治、模板、评测和生态兼容，避免在核心流程不稳定时继续增加入口。

每次迭代只接受一个可以从入口走到验收结果的完整切片，并在提交说明中写明用户场景、变更边界、自动化测试、浏览器证据和剩余风险。任何无法被用户操作和测试证明的“完成”，都只能标记为设计或实验状态。
