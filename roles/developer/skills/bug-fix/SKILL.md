# Bug 修复

不盲目乱改。先搞清楚问题，再按可能性排序尝试修复，修好一个就停，最后验证。

## Step 1：复现与定位（信息不足先问，不要猜）

提方案前必须先收集：

1. **完整错误信息**：报错堆栈、错误码、失败输出，不要只看一行。
2. **复现步骤**：什么操作触发了问题，能否稳定复现。
3. **环境信息**：语言/依赖版本、平台、最近的相关改动（`git log`、`git diff`）。
4. **定位范围**：读相关代码，追踪实际执行路径，缩小到可疑的具体位置。

> 信息不够时，先补充提问或自己去查，**禁止带着未验证的假设直接改**。

## Step 2：生成按优先级排序的修复方案

一次性列出所有合理方案，按"副作用从小到大"排序：

```
## 修复方案（按优先级排序）

| 优先级 | 方案 | 依据 | 风险 |
|--------|------|------|------|
| 1 | [最小改动方案] | 为什么最可能命中根因 | 低 |
| 2 | [局部逻辑修改] | 依据 | 中 |
| 3 | [较大变更] | 依据 | 高 |
```

**排序原则**：先无副作用的小改动（配置、参数、边界判断）→ 局部逻辑修改 → 依赖/架构变更 → 大范围重构。**拒绝一上来就重构。**

## Step 3：逐个尝试，成功即停

- 从优先级最高的方案开始，**一次只试一个**，不要同时叠加多个改动。
- 每个方案实施后**立即用最小代价验证**（跑相关测试/复现步骤）。
- 某个方案解决了根因，**就停**，不要为了"顺手"再改别的。
- 一个方案无效就**回退它**，再试下一个，并记录"已排除方案及原因"。

## Step 4：回归验证与交付

修复后必须：

- 跑与改动**直接相关**的测试、类型检查或构建，记录真实结果。
- 确认没有引入新问题（相关的已有测试仍通过）。
- 交付说明：根因是什么、改了哪些文件、用了哪个方案、验证命令与结果、还有什么没覆盖到。

## 红线

- 没有跑过的验证不得声称"已修复"。
- 不得用"注释掉测试""跳过检查"来让报错消失。
- 根因不明时，交付"已定位到 X、已排除 Y/Z、建议下一步"，而不是假装修好。
