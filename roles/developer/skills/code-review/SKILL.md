# 代码审查

对实现后的代码改动做质量检查，发现问题、评估风险、给出可执行的改进建议。

## 不使用时机

- 纯问答、概念解释，没有实际代码变更。
- 纯文案、排版、命名讨论，不涉及可执行逻辑。
- 用户明确只要一句“快速建议”，不需要正式审查。

## 审查流程

### Step 1：判定审查目标

- **本地改动审查**（默认）：审查当前工作区的未提交变更或指定文件。
- **指定范围审查**：用户给出具体文件、目录或对比范围（base...head）。

明确本次只审查哪些文件，避免范围蔓延。

### Step 2：取证，而不是只看片段

在下结论前收集最小必要上下文：

- 先跑 `git status` 和 `git diff`（或读取任务提供的 diff），确认改了什么、影响哪些模块。
- 阅读被改文件的**完整上下文**和它的**调用方/被调方**，不要只看改动的几行就下结论。
- 涉及行为变更时，找到相关的测试，确认是否同步更新。

### Step 3：预检门禁（优先用规则，不靠感觉）

在人工判断前，先执行项目已有的自动化检查（如可用），并把结果作为审查输入：

- 按项目类型探测并运行：测试、类型检查、lint、构建。
- 命令不明的项目，先读 `package.json` 的 scripts / `Makefile` / `go.mod` / `pyproject.toml` 等确定。
- 检查失败本身就是审查发现，不要绕过。

### Step 4：分级输出审查报告

按严重度分级，每条给出**位置、问题、理由、建议**：

```
## 审查结论：通过 / 通过(带建议) / 需修改

### 阻断（必须修复后才能交付）
- [文件:行号] 问题描述 → 为什么是错的 → 怎么改

### 建议（不阻断，但值得改）
- [文件:行号] 问题描述 → 影响 → 建议

### 已验证项
- 自动化检查：跑了哪些命令，结果如何
- 覆盖：改动是否有对应测试
```

## 审查重点（按风险优先级）

1. **正确性**：逻辑错误、边界条件、空值/异常路径、并发与竞态。
2. **安全**：注入、越权、密钥泄露、未校验的外部输入、危险操作（删除/覆盖）。
3. **兼容性**：破坏公共 API、改变既有行为、影响未提交或他人改动。
4. **可维护性**：明显的重复、过度复杂、与项目既有风格冲突。

## 输出要求

- 区分**事实**（代码里确实存在的问题）和**推断**（可能的风险），不夸大。
- 没跑过的检查不得声称通过；没读到的代码不得断言没问题。
- 阻断级问题交给 Bug 修复流程处理；审查本身不擅自修改代码。
