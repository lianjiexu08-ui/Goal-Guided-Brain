# 开发流程五步法

需求理解 → 方案设计 → 代码实现 → 代码审查 → Bug 修复。每一步都有明确的输入、交付物和"什么时候算做完"。不要跳步，不要把"写完代码"当成"交付完成"。

## 总原则

- 先读 README、AGENTS.md 和构建配置，检查 `git status`，识别并保留已有未提交修改。
- 陌生或大型项目，先用 **project-map** 建立项目地图，再动手。
- 每个阶段产出可检查的交付物；没跑过的检查不得声称通过。
- 不主动提交、推送、部署；不覆盖他人未提交的修改。

## 各阶段要点

### 1. 需求理解
明确要做什么、验收标准是什么、约束（时间/兼容/风格）。区分**已确认需求**、**假设**和**待确认问题**；假设和待确认项不要当作事实往下做。

### 2. 方案设计
基于需求定技术方案：模块划分、技术选型（优先沿用项目已有栈）、关键权衡（给理由）、接口契约。方案写到可指导实现的程度即可，不过度设计。

### 3. 代码实现
按方案逐模块实现：遵循项目既有风格、单一职责、必要注释、校验外部输入、有意义的错误处理。每改一处，追踪实际代码路径，保持最小必要修改。

### 4. 代码审查 → 用 **code-review**
实现完成后，用 code-review 流程复核 diff：取证（读完整上下文）→ 预检门禁（先跑自动化检查）→ 分级报告。发现阻断级问题进入 Bug 修复。

### 5. Bug 修复 → 用 **bug-fix**
遇到报错、测试失败或审查发现的阻断问题，用 bug-fix 流程：复现定位 → 多方案排序 → 逐个尝试成功即停 → 回归验证。

## 验证（贯穿 3/4/5 步）

- 运行与修改**直接相关**的测试、类型检查或构建，记录实际命令与结果、失败原因。
- 项目命令不明时，先读 `package.json` scripts / `Makefile` / `go.mod` / `pyproject.toml` 确定。

## 交付说明（每次交付都要给）

- 改了什么、涉及哪些文件。
- 验证命令与真实结果（哪些跑过、哪些没跑）。
- 剩余限制、风险或待确认项。
