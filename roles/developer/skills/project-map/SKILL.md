# 项目地图

目标：**不试图读完所有源文件**，用最少的阅读建立一张可行动的项目地图，让后续开发任务不再冷启动，也让团队其他成员直接复用。

## 什么时候做

- 第一次接触一个仓库，或要改动不熟悉的模块前。
- 团队需要一份"项目长什么样、怎么跑、怎么测"的共识时。
- 产出会写入**跨团队共享上下文**（`share_context`），供其它团队/成员读取。

## 三步阅读法（每步都可提前停止）

### 1. 看轮廓（判断项目类型与技术栈）

- 目录树（排除 `node_modules` / `dist` / `build` / `vendor` / `.git`）。
- 构建与依赖文件：`package.json` / `go.mod` / `pom.xml` / `pyproject.toml` / `Cargo.toml`。
- README、AGENTS.md、docs/。

→ 得出：这是什么项目、用什么栈、大致分几层。

### 2. 看骨架（找到入口与模块职责）

- 入口文件读全文（main / index / app / server 启动点）。
- 路由 / 接口定义 / 类型定义 / 配置文件。
- 每个顶层目录**一句话**说清它负责什么。

→ 得出：程序从哪启动、请求/数据怎么流动、模块边界。

### 3. 跟一个完整例子走一遍

挑一个有代表性的功能或请求，从入口追到结束，串起"入口 → 处理 → 存储/输出"的完整链路。

→ 得出：一个真实操作在代码里是怎么跑通的。

## 必须落到项目地图里的关键信息

- **启动命令**：怎么跑起来（dev / start / run）。
- **验证命令**：怎么跑测试、类型检查、lint、构建（写明具体命令）。
- **入口与核心模块**：路径 + 一句话职责。
- **约定**：代码风格、目录约定、不能踩的坑（已知限制、TODO）。
- **术语表**：至少 3 条项目特有的概念/缩写。

## 输出与共享

- 把地图写入共享上下文：`share_context`，key 用 `project-map/<项目名>`，kind 用 `note`。
- 内容**逐字来自真实文件**：路径、命令、模块名要和仓库一致，**不编造**；不确定的标注"待确认"。
- 后续任务开工前先 `read_shared_context` 读这份地图，避免重复摸瞎；代码大改后更新同一 key（带 `expectedRevision`）。
